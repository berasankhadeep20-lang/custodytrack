# Module Breakdown — CustodyTrack

Version 0.1

---

## 0. One gap surfaced while doing this breakdown

Working through the QR flow file-by-file exposed something `API.md` glossed over: **the OTP
path and the QR path aren't actually symmetric.** OTP is entered *by the attendant*, who is
already authenticated — so `ack_berth` (needs an authenticated `actor_id`) works fine for it.
QR is scanned *by the passenger*, on their own phone, with no login at all. Calling the same
authenticated RPC from an anonymous passenger session doesn't work.

**Fix:** the QR code encodes a short-lived signed token (berth ID + expiry, generated by the
attendant's authenticated session when they open the QR modal), not the berth ID directly. A
second RPC, `ack_berth_via_qr(token)`, validates the token server-side and performs the same
insert `ack_berth` does — but takes a token instead of relying on `auth.uid()`. This needs one
new migration file (below) and one new API function; everything else in `API.md` and
`SCHEMA.md` stands as written. Flagging this now, before implementation, is exactly why we do
module breakdown as its own step instead of jumping straight to code.

## 1. Frontend structure (`frontend/src/`)

```
src/
├── db/
│   ├── schema.js          # Dexie (IndexedDB) table defs: cachedBerths, cachedItems, outbox
│   ├── outboxRepo.js       # enqueue(event), listPending(), markSynced(id), incrementRetry(id)
│   └── cacheRepo.js        # getBerthChart(coachId), upsertBerthChart(data) — local read-through cache
│
├── sync/
│   ├── connectivity.js     # wraps navigator.onLine + a lightweight ping, exposes isOnline()
│   └── syncEngine.js       # the outbox drain loop: on reconnect + periodic timer,
│                            # pulls from outboxRepo, calls custodyApi, applies the
│                            # ok/duplicate/auth/validation/network taxonomy from API.md,
│                            # exponential backoff on network failures
│
├── api/
│   ├── supabaseClient.js   # single Supabase client instance (URL + anon key)
│   └── custodyApi.js       # thin typed wrappers: issueItem(), returnItem(), ackBerthOtp(),
│                            # ackBerthQr(token), fetchBerthChart(coachId), fetchUnresolved(filters)
│
├── features/
│   ├── attendant/
│   │   ├── BerthList.jsx        # renders all berths for the attendant's assigned coach
│   │   ├── BerthCard.jsx        # per-berth: 5 item toggles + ack status badge
│   │   ├── AckModal.jsx         # OTP-or-QR choice; delegates to one of the two below
│   │   ├── OtpEntry.jsx         # attendant enters passenger-read-out OTP
│   │   ├── QrDisplay.jsx        # renders QR encoding the signed token from ack_berth_via_qr setup
│   │   └── useBerthChart.js     # hook: merges cacheRepo (instant) + live subscription (when online)
│   │
│   ├── qr-confirm/
│   │   └── QrConfirmPage.jsx    # PUBLIC route, no login — passenger lands here from the scan,
│   │                            # one tap calls ack_berth_via_qr(token) directly
│   │
│   └── admin/
│       ├── ReconciliationDashboard.jsx  # unresolved_items table, filterable by train/date
│       └── LossAnalyticsChart.jsx       # Recharts bar chart, loss rate by route
│
├── components/              # shared: StatusBadge, Button, Layout, ConnectivityIndicator
└── App.jsx / routes.jsx     # route table — note qr-confirm is the one PUBLIC route,
                             # everything else requires an attendant/tte/admin session
```

**Why `qr-confirm/` is its own top-level feature folder, not nested under `attendant/`:** it's
not part of the attendant's authenticated app at all — it's a separate, public, one-page
surface the *passenger* opens. Keeping it structurally separate makes the auth boundary
visible in the file tree, not just in a comment.

## 3. Testing strategy (mapped to modules, so this isn't an afterthought later)

| Module | What gets tested | How |
|---|---|---|
| `db/outboxRepo.js` | Enqueue/dequeue correctness, retry counting | Unit tests (Vitest) against a real Dexie instance (fake-indexeddb) |
| `sync/syncEngine.js` | Correct handling of each response type from the taxonomy table | Unit tests with a mocked `custodyApi` returning each of the 5 outcomes |
| `006_qr_token_flow.sql` + `berth_acks` conflict path | Token expiry rejected; duplicate ack via either path returns `duplicate`, never a second row | Postgres-level tests (pgTAP or direct SQL assertions) — this is the correctness-critical part of the whole system, gets the most scrutiny |
| `features/attendant/*` | Issue → ack → return flow renders correctly per state | Component tests (React Testing Library) |
| End-to-end offline scenario | Go offline mid-flow, queue events, reconnect, confirm no duplicates land in Postgres | Playwright with network throttling, run against a local Supabase instance |
